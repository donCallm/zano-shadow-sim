# Симулятор сети для Zano: оценка осуществимости

**Дата:** 2026-08-23
**Статус:** Кабинетное исследование завершено — на всё, что выясняется чтением исходников, ответы получены. Код не писался, форки не создавались. Дальнейшая информация добывается только запуском (§10).
**Источники:** `hyle-team/zano` @ master, `Fountain5405/monerosim` @ `8f9209e6`, патч-лист `shadowformonero` v0.2.4 (`shadowformonero.md`).
**Вопрос:** применим ли подход monerosim — настоящие бинарники монеты внутри Shadow — к Zano, сколько это стоит и на что ответит.

---

## 1. Исходная точка

**monerosim** = генератор конфигов на Rust + агентный фреймворк на Python + форк Shadow
(`shadowformonero`), запускающий **настоящие бинарники Monero** в виртуальной сети.
Отвечает на: распространение блоков и транзакций, топология P2P, приватность против
сетевого наблюдателя, репетиции хардфорков. Даёт детерминизм по сиду.

Не отвечает на: экономику майнинга, динамику реоргов (таймер выбирает одного
производителя на высоту), что-либо зависящее от сложности вне regtest-диапазона.

**Для Zano аналога не существует** — ни в `hyle-team` (41 репозиторий), ни стороннего.
У Zano есть публичный тестнет, Zano MCP (наблюдение за живой сетью) и формальный анализ
с Common Prefix.

**Сроки:** HF6 на блоке 3 833 000, ожидался 25–27 августа 2026. Zenith (чистый PoS,
15-секундные блоки, 4–6 подтверждений) в реализации, переход сети в 2027.

## 2. Ядро Zano: что говорит код

### PoS исполняется под Shadow без правок

- Стейкинг живёт **в кошельке**, не в демоне: `wallet2::scan_pos` (`src/wallet/wallet2.h:1199`)
- Запускается **idle-хендлером epee-сервера каждые 2 секунды**
  (`src/wallet/wallet_rpc_server.cpp:136,144`): `refresh()` → `scan_tx_pool()` →
  `try_mint_pos()` → сон
- Скан **ограничен**: свои выходы × сетка временных меток шагом `POS_SCAN_STEP = 15s`
  в окне `CURRENCY_POS_BLOCK_FUTURE_TIME_LIMIT = 1200s` — порядка 80 итераций на выход,
  затем возврат `API_RETURN_CODE_NOT_FOUND`

Ограниченная работа, обрамлённая RPC и таймером, — ровно тот профиль исполнения, который
нужен Shadow: симулированные часы двигаются только по системным вызовам.

**Следствие: консенсус PoS исполняется по-настоящему.** Реорги, эквивокация, поведение
при разделениях — настоящие, в отличие от monerosim, где производителя выбирает
пуассоновский таймер.

### PoW требует внешнего драйвера

`miner::worker_thread` (`src/currency_core/miner.cpp:385-433`) — это `while(!m_stop)`
вокруг ProgPoW-хеша **без системных вызовов** в горячем пути, та же патология, что
у майнер-потока monerod. Лечение то же: сложность 1 плюс внешний агент, дёргающий
одноразовые RPC.

### DAG ProgPoW — не блокер

`contrib/ethereum/libethash/ethash.cpp:22-26`:

| | epoch 0 | epoch 127 (мейннет сегодня) |
|---|---|---|
| Полный DAG | 1024 МБ | ~2040 МБ |
| Light-кеш | 16 МБ | ~31 МБ |

`get_block_longhash` (`src/currency_core/basic_pow_helpers.cpp:64`) берёт **полный**
контекст и вызывается на **пути валидации** (`blockchain_storage.cpp:2267, 2591, 7657`).

Но аллокация — `std::calloc` (`ethash.cpp:145`), то есть анонимный mmap, а `full_dataset`
заполняется **лениво**. Эагерно строятся только light-кеш и l1-кеш (`:172-174`). Реальный
RSS — это light-кеш плюс тронутые элементы; гигабайты остаются виртуальным адресным
пространством, не физической памятью.

Light-патч всё равно стоит сделать (~10 строк) как гигиену: API уже есть
(`contrib/ethereum/libethash/ethash/progpow.hpp:30,36,39`), а идентичность результата
доказывается по коду (`progpow.cpp:287-317`) — полный путь есть мемоизация над той же
`calculate_dataset_item_2048`, которую вызывает light-путь.

### Стартовая сложность уже настроена

`src/currency_core/currency_config.h:129` открывает `#ifndef TESTNET`, и в **мейннет**-ветке:

    #define DIFFICULTY_POS_STARTER  1     // :135  <- мейннет
    #define DIFFICULTY_POW_STARTER  1     // :87
    #define POS_START_HEIGHT        0     // :62

Значение 5e18 — это testnet-ветка (`:147`). Пол PoS-сложности в
`blockchain_storage.cpp:1519` закрыт условием
`#if defined(TESTNET) && (CURRENCY_FORMATION_VERSION > 103)`, а в тестнете ровно 103 —
значит **код мёртв даже в testnet-сборке**.

Прочее: `DIFFICULTY_POS_TARGET = DIFFICULTY_POW_TARGET = 120s`,
`DIFFICULTY_TOTAL_TARGET = 60s`, `P2P_DEFAULT_MAX_CONNECTIONS_PER_IP = 3` (лучше
монеровской единицы, которую этому проекту пришлось поднимать до 4 — см.
`docs/20260605_max_connections_per_ip_bug.md`).

### Рантайм-конфиг — ключевая находка

`src/currency_core/core_runtime_config.h:105`:

    struct core_runtime_config {
      core_time_func_t      get_core_time;   // <- замещаемый источник времени
      hard_forks_descriptor hard_forks;      // <- set_hardfork_height(id, height)
      std::array<int, ZANO_HARDFORKS_TOTAL> min_build_numbers_for_hard_forks;
      uint64_t pos_minimum_heigh, min_coinstake_age;
      wide_difficulty_type  max_pos_difficulty;
      uint64_t pre_hardfork_tx_freeze_period;
    };

`blockchain_storage::set_core_runtime_config()` (`:8524`) существует и распространяет
конфиг по сервисам; тесты им пользуются. **В командную строку не выведено** — это
единственный кусок настоящего кода, который надо написать.

Для сравнения: monerosim держит `patches/monero-fakechain-hardforks.patch`, чтобы
получить эквивалент в Monero. В Zano вся механика уже внутри, включая подменяемые часы.

### Готовые драйверы блоков в тестовом дереве

`tests/core_tests/chaingen_helpers.h` — в шапке прямо сказано, что хелперы предназначены
для использования вне core_tests:

- `:23` `mine_next_pow_block_in_playtime` — `get_block_template` с
  `ignore_pow_ts_check = true`, подгонка timestamp для удержания низкой сложности,
  `find_nonce_for_given_block`, `handle_incoming_block`. Это **готовый прототип
  RPC-метода `generateblocks`**, которого Zano не хватает.
- `:228` `mine_next_pos_block_in_playtime_with_wallet` — `fill_mining_context` →
  `scan_pos` → `build_minted_block`.
- `tests/core_tests/chain_switch_pow_pos.cpp` — **уже существующий** тест переключения
  цепи между PoW и PoS.
- `test_core_time` — мокируемые часы.

### Genesis

- Коинбейза genesis — захардкоженный блоб `ggenesis_tx_raw` (`src/currency_core/genesis.h`),
  собирается в `generate_genesis_block()` (`currency_format_utils.cpp:4305`)
- `bl.nonce = CURRENCY_GENESIS_NONCE = CURRENCY_FORMATION_VERSION + 101011010121`
  (`currency_config.h:16`)
- **Рабочий инструмент:** `connectivity_tool --generate-genesis <config.json>
  --genesis-split-amount N` (`src/connectivity_tool/conn_tool.cpp:57,300`), читает JSON
  со списком адрес → сумма
- **Не** использовать `tests/functional_tests/generate_test_genesis.cpp` — всё тело под
  `#if 0` с 2020 года

Премайн критичен: **без профинансированных балансов PoS не стартует никогда.**

## 3. Режим для симулятора

Третий **вариант сборки** (как testnet), а не новый режим консенсуса. Консенсусная логика
не трогается.

    CURRENCY_FORMATION_VERSION = <своё>  -> свой genesis-нонс + свой network id
                                           (P2P_NETWORK_ID_VER = CFV + 0, :153)
    консенсус                            -> мейннет-ветка как есть (PoS/PoW стартер = 1)
    genesis                              -> connectivity_tool --generate-genesis
    чекпойнты                            -> отключить (create_checkpoints(), compile-time)
    высоты хардфорков                    -> проброс в CLI из core_runtime_config  <- код

Одна константа даёт и отдельную цепь, и изоляцию сети: ноды симулятора не смогут
захендшейкаться с мейннетом или тестнетом.

**Уже в командной строке демона, писать не надо:** `p2p-bind-ip`, `p2p-bind-port`,
`p2p-external-port`, `add-peer`, `add-priority-node`, `use-only-priority-nodes`,
`seed-node`, **`hide-my-port`** (механизм `reachable_fraction` / `hidden_fraction` этого
проекта — см. `docs/20260722_node_reachability_firewall.md`), `offline-mode`,
`allow-local-ip`, `disable-upnp`, `rpc-server-threads`, `p2p-server-threads`, `db-engine`.

### RPC: карта переименований, не редизайн

| monerosim вызывает | В Zano |
|---|---|
| `get_info` | `getinfo` |
| `get_height` | `getheight` |
| `get_block_count` | `getblockcount` |
| `get_block_header_by_height` | `getblockheaderbyheight` |
| `transfer`, `get_balance`, `get_transfers`, `open_wallet` | есть |
| `get_alternate_chains` | `get_alt_blocks_details` (близкий аналог) |
| `sync_info` | нет — собирать из `getinfo` |
| **`generateblocks`** (8 мест вызова, самый частый) | **нет — портировать из тестового хелпера** |

Обе формы написания восходят к оригинальному CryptoNote; Monero сохранил обе.

## 4. Форк Shadow: патчи переносятся

Разбор `shadowformonero.md` @ v0.2.4 — 11 патчей, ~2400 добавленных строк в 26 файлах.

| # | Патч | Строк | Для Zano | Основание |
|---|---|---|---|---|
| 1a | `unbound_interpose.c` | **667** | **не нужен** | в Zano **нет libunbound**; DNS через `boost::asio::ip::tcp::resolver` (`src/p2p/net_node.inl:415-421`) |
| 1b | `shim_api_addrinfo.c` | 324 | **нужен** | это путь `getaddrinfo`, которым Zano и пользуется |
| 2 | `sendmmsg` | ~100 | под вопросом | прямых вызовов в Zano нет; у Monero, вероятно, приходил из libunbound. Решается `strace` |
| 3 | Опции сокетов (IP_TOS, TCP_NODELAY, TCP_KEEP*) | ~80 | **нужен** | boost::asio их выставляет |
| 4 | SO_REUSEADDR + очистка CLOSED-сокетов | ~120 | **нужен** | `contrib/epee/include/net/abstract_tcp_server2.inl:482` — тот же файл epee |
| 5 | `mlock`/`mlock2`/`mlockall`/`msync` (LMDB) | 222 | **нужен** | `src/CMakeLists.txt:174` линкует lmdb; `--db-engine` по умолчанию `"lmdb"` |
| 6 | Credential-syscalls (`setres*id`) | 125 | не нужен | вызовов нет. Безвреден, если оставить |
| 7 | `setpriority` | малый | не нужен | вызовов нет. Безвреден |
| 8 | **Приоритет конструктора RNG = 101** | 33 | **нужен, байт-в-байт** | `src/crypto/initializer.h:8` содержит `__attribute__((constructor(101)))`, копирайт «2012-2013 The Cryptonote developers» — тот же файл, что у Monero |
| 9 | `_exit` после SIGKILL | ~5 | **нужен**, универсален | — |
| 10-11 | config / manager / formatter / handler | ~80 | инфраструктура | — |

**Ни один патч не требует переписывания под Zano.** Каждый либо применяется без
изменений, либо не нужен. Все адресуют поведение, унаследованное обоими проектами
от CryptoNote и epee, либо универсальные библиотеки (LMDB, boost::asio).

- Отпадает: ~800 строк
- Переносится без изменений: ~860 строк
- Под вопросом: ~100 (sendmmsg)

**Самый большой и самый хрупкий патч Zano не нужен.** `unbound_interpose.c` — это 28%
набора, ручная сборка запросов RFC 1035 и реконструкция структур `ub_result`. Он
существует потому, что libunbound открывает внутренние TCP-сокеты, которые никогда не
вызывают `connect()`, и Shadow отваливался по таймауту через 15 секунд с нулевым
результатом. Zano никогда не переходил на libunbound.

**Патч, от которого зависит детерминизм, совпадает точно.** Если инжектор Shadow
загружается после RNG-инициализатора монеты, процесс читает **настоящий**
`/dev/urandom`, и детерминизм ломается молча. У Zano `initializer.h` и `random.c`
унаследованы от CryptoNote без изменений, поэтому приоритет 101 идентичен.

## 5. Эксплуатационные находки

**Линковка динамическая — риск снят.** `CMakeLists.txt:217` добавляет `-static-libgcc
-static-libstdc++`, но полного `-static` нет. Весь механизм Shadow держится на LD_PRELOAD;
статически слинкованный бинарник никогда не был бы перехвачен. Проверять стоило до
сборки, а не после.

**UPnP включён по умолчанию — `--disable-upnp` обязателен.**
`src/daemon/daemon.cpp:156,331` запускает `miniupnp_helper.start_regular_mapping()`, если
флаг не передан. Под Shadow SSDP-мультикаст на 239.255.255.250 либо не поддержан, либо
будет впустую висеть на каждой ноде. Это аналог монеровского `--no-igd`, и ему нужен
слот в генераторе конфигов.

**Дефолты потоков вдвое тяжелее монеровских.** `rpc-server-threads` = 10
(`src/rpc/core_rpc_server.h:20`) и `p2p-server-threads` = 10, то есть ~20 потоков на
демон из коробки — 10 000 потоков на 500 нодах, и все планирует Shadow. Минимум для RPC
равен 2, ниже демон завершается (`daemon.cpp:427-431`, `return false`). Ставить
`--rpc-server-threads 2 --p2p-server-threads 2` с первого дня, иначе упрётесь в потолок
масштаба и будете винить Shadow.

**Build-number гейтинг — готовый рычаг для сценария «не все обновились».**
`min_build_numbers_for_hard_forks` живёт в рантайм-конфиге
(`core_runtime_config.h:119,126`), а `PROJECT_VERSION_BUILD_NO` — константа бинарника.
Два рычага: разные бинарники по build-номеру, либо (дешевле) один бинарник с разным
рантайм-расписанием хардфорков на ноду — именно так этот проект делает через
`monerod-hf`.

**Не использовать `--db-engine mdbx`.** Zano линкует и LMDB, и MDBX; патч №5 писался под
LMDB. Оставаться на дефолте.

кошелька + внешний драйвер, причём стейкинг там уже штатно живёт в кошельке под
idle-таймером.

## 7. Решения, которые принять до кода

**Кошелёк обязателен для стейкинга, и это меняет экономику масштаба.** В monerosim
relay-ноды — **только демон**, чем и достигается доступность 1000+ узлов. В Zano стейкер
это демон + кошелёк + драйвер; дешёвой может быть только не-стейкящая нода. Планировать
память соответственно: сколько нужно стейкеров для эксперимента, столько полных троек и
поднимать, остальное добивать relay-нодами ради реализма топологии.

**Genesis — курица и яйцо, оставить запас заранее.** Порядок односторонний:

    кошельки стейкеров -> JSON с адресами -> connectivity_tool --generate-genesis
      -> вкомпилировать в genesis.h -> пересобрать zanod -> запускать

**Кошельки становятся частью сборки.** Смена состава стейкеров означает пересборку.
Сгенерировать избыток один раз (скажем, 200 предфинансированных аккаунтов) и раздавать
подмножества по сценариям.

**Стартовое время симуляции против сетки меток PoS.** Genesis несёт `timestamp = 0`;
кернел PoS работает по сетке шагом 15 с относительно медианы последних блоков, с окном
будущего 1200 с. Как это ляжет на начальный момент симулированных часов Shadow, чтением
не выяснить. Один из первых вопросов при поднятии трёх нод.

**Знать про `pre_hardfork_tx_freeze_period` заранее.** «Number of blocks before the
hardfork activation when no new txs are accepted (effective from HF5)». В сценариях
перехода транзакции перестанут приниматься за N блоков до активации. Это штатное
поведение, а не поломка стенда.

**Написать исследовательскую программу до платформы.** Дорогая часть monerosim — не код,
а знание, на какие вопросы стенд отвечает. Одна страница до начала: «эксперимент №1 —
распределение сетевой задержки при 15-секундных блоках на топологии CAIDA; метрика такая-то;
критерий успеха такой-то». Иначе через полгода будет платформа без исследовательской
программы — худший исход при вложении 6–9 месяцев и самый вероятный, если вопросы не
зафиксировать заранее.

**Критерии успеха делать специфичными для сценария.** Урок из прогонов §9: общие критерии
monerosim («блоки созданы», «блоки разошлись», «транзакции разосланы», «транзакции в
блоках») дают ложные срабатывания в обе стороны — провал там, где сценарий не
предусматривает пользователей, и зелёный результат там, где про разделение сети не
сказано ничего. Для форк-сценариев критерии должны проверяться машинно и по существу.

**Пинить версии с первого коммита.** `zano.pin` + `shadowformonero.pin`, с отказом
запускаться при рассинхроне, как в этом репозитории. На трёх нодах выглядит
преждевременно, на сотне незаменимо: «у меня не воспроизводится» иначе съедает недели.

### Обнаруженные дефекты monerosim

Три штуки, все стоит отправить апстрим:

1. **Имена пакетов для Ubuntu 26.04.** `setup.sh:366` перечисляет `libunwind8-dev` и
   `libreadline6-dev`; на 26.04 у обоих нет кандидата, правильные имена —
   `libunwind-dev` и `libreadline-dev`. `apt install -y` падает целиком при одном
   ненайденном пакете, так что установка зависимостей не проходит. `libunwind8-dev`
   встречается также в `setup.sh:866`.

2. **Счётчик процессов не видит форк-бинарник.** `run_sim.sh:1139` сравнивает имя
   процесса точно (`monerod)`), тогда как для кошельков стоит маска (`monero-wa*`).
   Форк-конфиги запускают `monerod-hf`, поэтому монитор показывает «0 monerod» и
   «Monerod 0 KB», занижая итог по памяти на гигабайты. Чинится маской `monerod*`.

3. **Критерии успеха не знают о сценарии.** `hf_micro_2node` объявлен провалившимся,
   потому что не было транзакций, — но в конфиге ноль пользователей, и это правильное
   поведение. `hf_split_5m2u` объявлен полностью успешным, хотя четыре общих критерия
   прошли бы одинаково и при несработавшем форке: про разделение они не говорят ничего.
   Настоящие критерии для форк-сценариев лежат в шапках конфигов и проверяются вручную
   по таблице высот в `summary.txt` и логам демонов. Дополнительно: сводка сообщила
   «Alerts: 6», тогда как `monitoring/final_report.json` содержит `alerts: 0`.

### Ловушка с местом на диске

Виртуальный диск WSL — разреженный файл на хосте. `df` внутри WSL показывает виртуальный
размер (сотни гигабайт) вне зависимости от того, сколько физически осталось. Когда на
хосте кончилось место, vhdx не смог расти, ext4 ушёл в аварию, и любой бинарник стал
недоступен с `Input/output error`; WSL после этого не стартовал вовсе.

Один прогон quickstart стоит около 700 МБ (436 МБ архив плюс `shadow.data` во время
работы). **Следить надо за свободным местом хоста, а не за `df` внутри WSL**, и чистить
`archived_runs/` (`scripts/prune_archives.sh`, флаг `--no-archive` у `run_sim.sh`).

## 12. Оговорка по срокам

**Кода Zenith публично ещё нет** — он в реализации, переход сети в 2027. Всё описанное
выше касается сегодняшнего гибридного Zano.

Это довод в пользу того, чтобы начинать сейчас: строить стенд **против гибрида**, который
существует и тестируем сегодня. К моменту появления кода Zenith будет откалиброванный
работающий инструмент, а не проект с нуля под дедлайн. Адаптация под чистый PoS окажется
**упрощением** — отпадут и внешний драйвер PoW, и возня с ProgPoW.

Обратный порядок — ждать Zenith и потом начинать — не успевает.

Важное уточнение по точности в гибридной фазе. Форки возникают по трём разным причинам,
и подделка PoW затрагивает их неодинаково:

| Причина форка | В гибриде |
|---|---|
| Ноды отвергают блоки по несовместимой версии («n% не обновились») | **настоящий** — разделение создают правила консенсуса |
| Сеть физически разорвана, стороны тянут независимо | **настоящий** — разрыв на сетевом уровне |
| Два производителя нашли блок почти одновременно | **половина настоящая** — PoS-сторона да, PoW-сторона подделана |

Сценарии перехода и разделения работают честно уже в гибриде. Занижена будет только
частота осиротевших блоков от одновременного нахождения — а это вопрос параметров Zenith
(15-секундные блоки, глубина подтверждений), то есть фазы чистого PoS, где подделывать
уже нечего.

## 13. Зачем это Zenith

Формальный анализ с Common Prefix даст результаты безопасности, параметризованные
**границей сетевой задержки**. Чему эта граница равна в реальной сети Zano — вопрос
эмпирический.

При 15-секундных блоках он становится острым. Сейчас распространение блока занимает
единицы секунд против 60-секундного интервала — около 5%, шум. При 15 секундах та же
задержка составляет 20-30% интервала. В этом режиме она управляет частотой осиротевших
блоков, глубиной форков и обоснованностью выбора «4-6 подтверждений».

Симулятор на реальной топологии CAIDA измеряет распределение задержки. Формальный анализ
его потребляет. Стык численный, а не риторический.

И компромисс по точности падает удачно: грубо моделируемая половина (внешний драйвер PoW)
— ровно та, которую Zenith удаляет. Моделируем грубо то, что уходит; исполняем честно то,
что остаётся.

## 14. Что показывать разработчикам Zano

Планка: у них уже есть тестнет, Common Prefix и `core_tests`. Показывать имеет смысл
только то, чего эти три вещи не дают.

**Уровень 1 — меняет решение:**

1. **Измеренная граница сетевой задержки при 15-секундных блоках** — распределение
   «время до момента, когда блок увидели 50/90/99% нод» на топологии CAIDA с разносом по
   шести континентам. Тестнет слишком мал и однороден; формальный анализ это потребляет,
   а не производит.
2. **Частота осиротевших блоков и обоснование глубины подтверждений** — 15 с против
   текущих 60 с на одной топологии.
3. **Свип по «n% стейка не обновилось»** — n = 5, 10, 20, 30, 40%, по несколько сидов на
   точку. Шаблон отработан (§9): две цепи, транзакции подтверждаются на отставшей.
   Тестнет даёт одну попытку, симулятор — пятьдесят, воспроизводимых по сиду.

**Уровень 2 — без этого первому не поверят:**

4. **Калибровка по живой сети** — предусловие, не опция. Образец:
   `docs/20260620_network_topology_study.md`, где сверка с четырьмя измеренными
   метриками мейннета вскрыла, что симулятор запускал «идеальную сеть» вместо
   мейннетовских ~15% reachable.
5. **Разделение сети в момент активации** — единственный тест из списка, требующий
   доработки форка Shadow (`docs/netsplit_scenario_mods.md`).
6. **Стейк офлайн и концентрация стейка** — класс вопросов, которого у PoW-сети нет.

**Уровень 3 — обычно и переубеждает:** конкретная находка в поведении P2P на плотности.
Репутация monerosim строится не на графиках, а на найденном баге
(`docs/20260605_max_connections_per_ip_bug.md`): 31 180 отказов в соединении за прогон на
15 нодах. У Zano дефолт `max-connections-per-ip` равен 3 — лучше, но не факт, что
достаточно.

**Чего оно не покажет, и это стоит проговорить самим:** криптографическую корректность
Zarcanum и Zenith (работа Common Prefix), экономику стейкинга, эффекты абсолютных
значений сложности.

Все шесть — про разрыв между Ubuntu 26.04 и тем, на чём Zano тестировали (README

### Правка mdbx (отклонение №4)

Единственное место использования во всём дереве. `contrib/db/libmdbx/src/elements/osal.h`,
строка 431:

    -#if __has_extension(c_atomic) || __has_extension(cxx_atomic)
    +#if defined(__clang__) && (__has_extension(c_atomic) || __has_extension(cxx_atomic))

Команда:

    sed -i '431s@.*@#if defined(__clang__) \&\& (__has_extension(c_atomic) || __has_extension(cxx_atomic))@' \

### Компилятор — системный gcc 15, откат невозможен

Попытка перейти на gcc-12 (внутрь протестированного Zano диапазона) провалилась на линковке:

    libboost_serialization.so.1.83.0: undefined reference to '__cxa_call_terminate',
    version 'CXXABI_1.3.15'

Механизм: `CMakeLists.txt:217` добавляет `-static-libstdc++`, из-за чего подтягивается
статическая libstdc++ **того компилятора, которым собирают**. У gcc-12 в ней нет символов
`CXXABI_1.3.15`, а системный Boost 1.83 собран gcc-15 и их требует.

Вывод: компилятор и Boost должны быть из одной сборочной эпохи. Раз Boost берём системный —
компилятор тоже системный. Альтернатива, если понадобится именно gcc-12, — собирать Boost
1.84 из исходников тем же компилятором, как и велит README Zano.

### Обязательные флаги запуска демона

    --no-predownload --disable-upnp --rpc-server-threads 2 --p2p-server-threads 2 --db-engine lmdb

**`--no-predownload` — находка, которую легко пропустить.** При первом запуске `zanod`
пытается скачать готовую базу блокчейна с внешнего хоста:

    Trying to download blockchain database from
    https://f005.backblazeb2.com/file/zano-predownload/zano_lmdb_95_3709300.pak ...

`--offline-mode` этого **не отключает** — механизмы разные. Внутри Shadow интернета нет,
поэтому каждая нода будет либо висеть, либо ждать таймаута HTTPS-запроса. Симуляция при
этом не падает, а необъяснимо буксует на старте, и искать причину пришлось бы в последнюю
очередь. Флаг `--no-predownload` объявлен в `src/common/command_line.cpp:38`.

Обоснование остальных флагов — в §5.

### Что из этого следует для проекта

Все шесть отклонений — про окружение, ни одного про код. Отсюда прямой вывод для фазы 5.5:
**пинить надо не только версии Zano и Shadow, но и всё сборочное окружение** — компилятор,
Boost, OpenSSL, binutils. Иначе очередное обновление дистрибутива обрушит сборку, и никто
не вспомнит эти шесть шагов.

Разумный вариант — зафиксировать окружение целиком (контейнер или скрипт установки с
явными версиями), а не полагаться на то, что окажется в системе.

### Память: виртуальная огромна, физическая ничтожна

Замер на простаивающем нативном демоне:

| | Значение |
|---|---|
| `VmSize` | 271 135 432 кБ ≈ **259 ГиБ** |
| `VmRSS` | 34 320 кБ ≈ **33,5 МиБ** |

Соотношение ≈ 7900 : 1. Источник виртуального резерва — **две** базы LMDB по 128 ГиБ
(`CACHE_SIZE` в `src/common/db_backend_base.h:9`, одна на блокчейн, одна на пул
транзакций) плюс гигабайт ethash.

Под Shadow на одной ноде это проблем не создало: `ru_maxrss` всего процесса Shadow
вместе с нодой — 0,154 ГиБ. На трёх нодах тоже. Поведение на сотне нод остаётся
непроверенным, но **физическая память не будет ограничителем** — 33 МБ на простаивающую
ноду против 255 МБ у `monerod` в сопоставимом прогоне.

Тем не менее в фазу 1 стоит добавить уменьшение `CACHE_SIZE` для симуляторной сборки:
regtest-цепи на несколько сотен блоков нужны мегабайты, а не 256 ГиБ резерва. Одна
константа снимает вопрос с виртуальным пространством целиком.

### Флаги, которые ломают пиринг

Найдено ценой нескольких часов отладки, поэтому вынесено отдельно.

**`--use-only-priority-nodes` использовать нельзя.** В Zano это не «подключаться только к
указанным пирам», а **безусловный отказ от всех входящих соединений**
(`src/p2p/net_node.inl:141`):

    bool node_server<t_payload_net_handler>::is_remote_ip_allowed(uint32_t addr, bool is_incoming)
    {
      if (m_offline_mode)
        return false;                    // ← offline-mode тоже режет входящие

      if (is_incoming)
      {
        // ... проверки лимитов по IP ...
        if (m_use_only_priority_peers)
          return false;                  // ← безусловно
      }
      ...
    }

С этим флагом три ноды звонят друг другу и все кладут трубку. В трассе выглядит так:
`accept` → `epoll_ctl(ADD)` → `getpeername` → `shutdown` через три микросекунды, ни
одного прочитанного байта.

**`--offline-mode` отвергает входящие первой же строкой той же функции.** Для сценариев
с намеренно изолированными нодами пригодится, случайно включать нельзя.

Для детерминированного пиринга годится `--add-priority-node=<IP>:<порт>` **без**
`--use-only-priority-nodes`.

### `--no-predownload` обязателен

При первом запуске `zanod` пытается скачать готовую базу блокчейна:

    Trying to download blockchain database from
    https://f005.backblazeb2.com/file/zano-predownload/zano_lmdb_95_3709300.pak ...

`--offline-mode` этого **не отключает** — механизмы разные. Внутри Shadow интернета нет,
поэтому каждая нода будет ждать таймаута HTTPS-запроса. Симуляция при этом не падает, а
необъяснимо буксует на старте. Флаг объявлен в `src/common/command_line.cpp:38`.

### Захардкоженные сид-ноды мейннета

Без `--add-priority-node` демон каждые две секунды долбится в реальные адреса Zano
(`ADD_HARDCODED_SEED_NODE`, `src/p2p/net_node.inl:443`), а Shadow отвечает
`Attempting to connect to address '195.201.107.230:11121' for which no host exists`.

Монеросим решает это **подстановкой фиктивных хостов** с адресами монеровских сидов
(`monero-seed-001..006` в его конфигах). Для Zano понадобится то же самое — пункт для
фазы 4.

### Минимальный конфиг достаточен

GML-топология, DNS-сервер и `bootstrap_end_time` из конфигов монеросима **не нужны** для
базового пиринга. Хватает:

    network:
      graph:
        type: 1_gbit_switch

`model_unblocked_syscall_latency` на результат не влияет (проверено включением и
выключением — цифры совпали до единицы).

### Методика отладки: что сработало

Три приёма, каждый из которых стоит применять раньше, чем перебирать гипотезы.

**1. Контрольный опыт.** Запустить `monerod` в **том же самом** минимальном конфиге. Он
спарился без правок — это мгновенно отделило «мой конфиг кривой» от «Zano несовместим» и
сузило поиск до специфики Zano. Стоило сделать первым делом, а не после часа перебора
параметров.

**2. Полная трасса Shadow.** `shadow --strace-logging-mode standard <config>` — это флаг
командной строки, **не** поле конфига. Пишет каждый системный вызов с аргументами и
возвратами в `shadow.data/hosts/<хост>/<процесс>.strace`. Только это дало ответ:
последовательность `accept` → `getpeername` → `shutdown` видна буквально.

**3. Правильное место для логов.** Вывод демонов лежит в
`shadow.data/hosts/<хост>/*.stdout`, `*.stderr` и `*.shimlog`, а не только в
собственном `zanod.log` внутри `--data-dir`. `shimlog` — лог LD_PRELOAD-перехватчика;
если демон делает что-то неожиданное для шима, жалоба будет именно там.

Полезный признак в агрегированных счётчиках Shadow (печатаются при `log_level: info`):
у работающего пиринга `recvfrom` заметно **больше** `sendto`, у сломанного они строго
равны — значит запросы уходят, а ответов нет.

### Непроверенная деталь

`--p2p-bind-ip` менялся с `0.0.0.0` на адрес хоста одновременно с другими правками, и
отдельно этот эффект не измерялся. Возможно, `0.0.0.0` тоже работает. Оставлено как у
монеросима — адрес хоста.

## 17. Сборка для симулятора: `ZANO_SIMNET` (пункт 1.1, 2026-08-24)

Симуляторная сборка — это **мейннет с одной переопределённой константой**, а не третья
полноценная ветка конфигурации. Мейннет-ветка уже даёт `DIFFICULTY_POS_STARTER = 1`,
`DIFFICULTY_POW_STARTER = 1`, `POS_START_HEIGHT = 0` и отсутствие пола PoS-сложности
(см. §2), поэтому семь блоков `#ifndef TESTNET` трогать не пришлось.

### Правки

`CMakeLists.txt`, рядом со строкой 76:

    set(ZANO_SIMNET FALSE CACHE BOOL "Compile for the Shadow simulator network")

и после блока `if(TESTNET)`:

    if(ZANO_SIMNET)
      if(TESTNET)
        message(FATAL_ERROR "ZANO_SIMNET and TESTNET are mutually exclusive")
      endif()
      message("!!!!!! NOTICE: Project is building for SIMNET !!!!!!")
      add_definitions(-DZANO_SIMNET)
    endif()

Взаимоисключение с `TESTNET` обязательно: иначе получится сборка с невнятной
идентичностью, где часть констант из одной ветки, часть из другой.

`src/currency_core/currency_config.h:10`:

    #ifndef TESTNET
    #  ifdef ZANO_SIMNET
    #    define CURRENCY_FORMATION_VERSION                  110
    #  else
    #    define CURRENCY_FORMATION_VERSION                  84
    #  endif
    #else
    #define CURRENCY_FORMATION_VERSION                      103
    #endif

### Допустимый диапазон значения: не более 117

Неочевидное ограничение, стоившее одной неудачной сборки. Первая попытка со значением 200
падает так:

    bc_offers_service.h:250: error: boost::mpl::less<int_<420>, int_<256>>

`BOOST_CLASS_VERSION` требует значение **строго меньше 256**, а константа
`BC_OFFERS_CURRENT_OFFERS_SERVICE_ARCHIVE_VER` зависит от формационной версии **дважды**:

    BC_OFFERS_... = CFV + BLOCKCHAIN_STORAGE_MAJOR_COMPATIBILITY_VERSION + 9
                  = CFV + (CFV + 11) + 9
                  = 2·CFV + 20

Отсюда **2·CFV + 20 ≤ 255, то есть CFV ≤ 117**. Ограничение накладывает не байт network
id (как можно подумать), а лимит boost-сериализации.

Значение 110 оставляет запас в семь единиц — при необходимости доступны варианты 111–117.

### Что даёт одна константа

| Константа | Формула | Мейннет | Симнет | Эффект |
|---|---|---|---|---|
| Нонс genesis | `CFV + 101011010121` | 101011010205 | 101011010231 | другой хеш genesis |
| Байт 15 network id | `CFV` | 84 | 110 | отказ в рукопожатии |
| Версия хранилища БД | `CFV + 11` | 95 | 121 | база мейннета не загрузится |
| Архив offers-сервиса | `2·CFV + 20` | 188 | 240 | — |
| Архив мемпула | `CFV + 31` | 115 | 141 | — |
| Хранилище P2P | `CFV + 14` | 98 | 124 | — |
| Peerlist | `CFV + 7` | 91 | 117 | — |
| `formation_ver` кошелька | `CFV` | 84 | 110 | кошелёк мейннета обрезается (`wallet2.h:190,197`) |

Network id собирается как UUID в `src/p2p/net_node.inl:25`, где формационная версия —
шестнадцатый байт, а десятый занят флагом тестнета.

### Границы: чего 1.1 не делает

- **Genesis по содержимому остаётся мейннетовским.** `src/currency_core/genesis.h`
  выбирает структуру блоба по `#ifndef TESTNET`, симнет наследует мейннетовскую
  (161 × `uint64_t` + 7 байт). Премайн уходит на адреса, которых у нас нет; цепь стартует,
  но **PoS не заведётся с пустыми балансами** — это пункт 1.4
- **Чекпойнты остаются мейннетовскими** — пункт 1.2. В `create_checkpoints` уже есть
  пустая ветка `#ifdef TESTNET`, так что достаточно добавить туда `ZANO_SIMNET`
- **Захардкоженные сид-ноды остаются мейннетовскими** — в симуляции недостижимы,
  глушатся через `--add-priority-node`; полное решение (фиктивные хосты, как у
  монеросима) — фаза 4
- **Высоты хардфорков остаются мейннетовскими** — на свежей цепи означает «никогда»,
  штатно перекрывается рантайм-конфигом в 3.1

### Чекпойнты отключены (пункт 1.2, 2026-08-24)

`src/currency_core/checkpoints_create.h:19` — одна строка:

    -#ifdef TESTNET
    +#if defined(TESTNET) || defined(ZANO_SIMNET)
    +    // no checkpoints for testnet and simnet

**Не косметика.** Верхний мейннетовский чекпойнт стоит на высоте 2 000 000, а
`is_in_checkpoint_zone` — это просто `height <= верхний`. Значит **каждый блок** цепи
стенда попадал бы в «зону чекпойнтов», и `handle_block_to_main_chain`
(`blockchain_storage.cpp:7610`) выставлял бы `m_is_in_checkpoint_zone = true` для всех.

В зоне пропускается вся криптографическая валидация:

| Строка | Что пропускается |
|---|---|
| 6055 | соответствие числа подписей числу входов |
| 6268 | валидация подписей — `return true` |
| 6356 | валидация входов — `return true` |
| 6486 | путь CLSAG — `return true` |
| 6526 | хеш префикса и доказательства — `return true` |
| 7756 | `tx.attachment.clear(); tx.signatures.clear(); tx.proofs.clear();` |

Стенд принимал бы транзакции без проверки подписей и вырезал бы доказательства из
хранилища. Причём **молча**: `check_block` для высот без чекпойнта возвращает истину,
ошибок в лог не идёт. Заодно исчезла бы стоимость проверки криптографии — та самая, что
задаёт потолок по интенсивности транзакций.

Пустой набор выключает зону целиком: `is_in_checkpoint_zone` возвращает ложь при пустой
карте (`checkpoints.cpp:31`), `get_top_checkpoint_height` возвращает 0 (`:50`), и условие
`m_db_blocks.size() < 0` при инициализации (`blockchain_storage.cpp:802`) не срабатывает.

Приёмка (хеши компилируются строковыми литералами, запуск не нужен):

    strings ~/zano/build-sim/src/zanod | grep -c 46a6c36d…   # 0  ✅
    strings ~/zano/build/src/zanod     | grep -c 46a6c36d…   # 1  ✅

Genesis не изменился — `d727ad15…`, как и должно быть: чекпойнты на него не влияют.

Запасной путь `--non-pruning-mode` (`src/common/command_line.cpp:43`) отвергнут: он
рантайм-флаг, забыть его на одной ноде из сотни означает получить ноду с отключённой
валидацией и не заметить; плюс его собственное описание предупреждает «Will terminate if
the DB was previously in (normal) pruning mode».

### Решение по `CURRENCY_NAME`

Оставлено `"Zano"` без суффикса. Изоляции достаточно семи механизмов выше, а каждое
лишнее расхождение с апстримом придётся сопровождать при обновлениях.

Следствие: каталог данных по умолчанию совпадает с настоящим клиентом, поэтому
`--data-dir` обязателен при каждом запуске. В фазе 4 стоит сделать его **обязательным
полем генератора конфигов**, а не значением по умолчанию — забыть его на сотне нод
означает записать поверх чужого блокчейна.

### Кошельки: 16 казначейских + 200 стейкеров

Двухслойная конструкция: в genesis попадают только казначейские, стейкеры финансируются
переводами во время прогона. Состав стейкеров меняется конфигом, без пересборки.

Три особенности `simplewallet`, каждая ломает наивный скрипт:

- **Два пробела** в строке вывода: `Generated new  wallet:` — следствие пустой вставки
  в `simplewallet.cpp:771`. Регулярное выражение должно допускать `\s+`
- **Код возврата 1 при успехе** (`simplewallet.cpp:4090`) — опираться только на разбор вывода
- **Seed неинтерактивно не извлекается**: `show_seed` (`:339`) спрашивает пароль трижды

Проверка: все 216 переоткрыты и отдали тот же адрес, ни одного `truncated` — то есть все
созданы симнет-сборкой, как требует `wallet2.h:190`.

### Найден баг в `connectivity_tool`

Первая попытка дала genesis, который кошелёк не смог разобрать:

    error on pulling blocks: acc_outs_lookup_error @ wallet2.cpp:655
    condition failed: o.target.type() == typeid(txout_to_key)

Причина — `conn_tool.cpp:355`. Переменная `de` объявлена **до** цикла с
`de.addr.resize(1)`, а внутри цикла стоит `de.addr.push_back(addr)`, который **накапливает**:

| Итерация | `de.addr` | Размер |
|---|---|---|
| 1 | [пустой, addr₁] | 2 |
| 16 | [пустой, addr₁ … addr₁₆] | 17 |

Получатель с несколькими адресами трактуется как **multisig**, и выход получается
`txout_multisig` вместо `txout_to_key`. А `lookup_acc_outs_genesis`
(`currency_format_utils.cpp:3879`) умеет только `txout_to_key`.

Исправление — одна строка, `de.addr.assign(1, addr)`. Подтверждение по двум признакам:
массив данных genesis сократился с **v[650] до v[104]**, и удельный размер сошёлся с
мейннетовским (52 байта на получателя против 50).

**Стоит отправить апстрим.** Мейннетовский genesis, судя по всему, собирали более старой
версией инструмента.

### Ключ в JSON называется иначе, чем поле

`currency_format_utils.h:120`:

    KV_SERIALIZE_N(amount_this_coin_fl, "amount_this")

В JSON ключ — **`amount_this`**, а не `amount_this_coin_fl`. С неправильным именем поле
молча не грузится, `amount_this_coin_int` остаётся нулём, и инструмент падает с
`unable to parse amount_this` в `process_payment_entrie` (`conn_tool.cpp:283`).

Ошибка видна только с флагом **`--do-console-log`** (`conn_tool.cpp:61`) — без него
вывод пустой и файлы просто не создаются.

Поля `paid_btc` и `btc_usd_price` заполнять **обязательно**: без них не срабатывает ни
одна ветка макросов `PROCESS_XXX_COIN_ENTRIE` (`:365–381`), статистика остаётся нулевой,
и самопроверки ругаются.

### Точность деления

`PREMINE_AMOUNT / 16 = 1 094 825 187 500 000 000` атомарных единиц, остаток ноль.
В монетах — `1094825.1875`, двоичная дробь `3/16`, представимая в `double` точно.
Обратное преобразование `round(fl * COIN)` в `conn_tool.cpp:316` сходится до единицы.

Это не автоматически: `amount_this_coin_int` объявлен как `double`, и при неудачном
выборе долей младшие разряды потерялись бы, разойдясь с базой эмиссии
(`currency_format_utils.cpp:4159`).

### Демон в изоляции отвечает `BUSY`

`core_rpc_server.cpp:110`:

    #ifndef TESTNET
        if (m_ignore_offline_status) return true;
        if (!m_p2p.get_payload_object().is_synchronized()) return false;
    #endif

В мейннет-сборке, которую симнет наследует, RPC отвечает `BUSY`, пока демон не считает
себя синхронизированным. Без пиров это не наступает никогда. В testnet-сборках проверка
вырезана препроцессором.

Лечится флагом **`--rpc-ignore-offline`** (`core_rpc_server.cpp:49`). Добавить в
обязательный набор для одиночных нод.

### Премайн заблокирован до высоты 10

Баланс показывает `unlocked 0.0 / total 1094825.1875` — выход из коинбейзы, флаг `m`.
`CURRENCY_MINED_MONEY_UNLOCK_WINDOW = 10` (`currency_config.h:38`), **ровно столько же,
сколько `min_coinstake_age`**. Отдельной проблемы нет: как только драйвер PoW выдаст
десять блоков, монеты станут и тратимыми, и пригодными для стейка.

### Открытый вопрос: дата создания кошелька

`wallet2.cpp:1716` пропускает блоки старше даты создания кошелька, а
`get_wallet_minimum_height` (`:1792`) выводит её через `GET_EST_HEIGHT_FROM_DATE`.
Кошельки создаются по реальным часам (2026), цепь стенда живёт в симулированном времени
с 2000 года — то есть кошелёк всегда «в будущем» относительно цепи.

На цепи высотой 1 это не помешало: оценка высоты по дате не может выйти за пределы цепи.
**Но на длинной цепи новый кошелёк может пропустить всё.** Проверить в фазе 2, когда
появятся блоки. Если подтвердится — лечится флагом `--no-set-creation-date`
(`simplewallet.cpp:130`), вызывающим `reset_creation_time(0)`; `wallet2::set_minimum_height`
существует (`:1787`), но наружу не выведен.

## 19. Механика PoS Zano под симулятором (пункт 2.4, 2026-08-24)

Разбор гибридного такта вскрыл три свойства PoS Zano, которых нет в документации
проекта и которые определяют устройство всех сценариев фаз 6–7.

### Условие победы делится на сумму стейка, и деление целочисленное

`src/currency_core/pos_mining.cpp:87`:

    wide_difficulty_type final_diff = this->basic_diff / this->stake_amount;
    found = currency::check_hash(this->kernel_hash, final_diff);

`stake_amount` — в атомарных единицах, монета это 10¹². Пока `basic_diff` меньше суммы
выхода, частное равно нулю и проверка проходит **с первой пробы, всегда**. Мейннетовская
`DIFFICULTY_POS_STARTER = 1` против выхода в одну монету означает мёртвую зону в
двенадцать порядков: ретаргет исправно растёт, но на темп не влияет вообще. Zano
печатает обе ветви в одном логе:

    difficulty: 105179487279220637, final_diff: 0        <- казна, 1,09e18
    difficulty: 104298457185056129, final_diff: 104298   <- награда, 1e12

**Следствие для сценариев:** выход, превышающий равновесную сложность, — это генератор
блоков вне досягаемости ретаргета, сдерживаемый только `min_coinstake_age`. Номиналы при
раздаче стейкерам обязаны быть заметно ниже равновесной сложности.

**Следствие для калибровки:** равновесная сложность пропорциональна суммарному стейку и
поэтому движется по ходу прогона. Замерено: 3,6·10¹⁶ при 86 стейкуемых монетах,
1,03·10¹⁷ при 437. Константа стартовой сложности задаёт лишь точку входа; выбирать её
надо чуть выше ожидаемого равновесия — сверху ретаргет спускается плавно, снизу
разгоняется на порядки и жжёт сотни блоков на прогрев.

### Перебор неподвижен между блоками

`build_stake_modifier` (`blockchain_storage.cpp:8481`) собирает модификатор из двух
величин: стейк-хеш последнего PoS-блока и хеш последнего PoW-блока. Модификатор входит в
хешируемый кернел (`build_kernel`, `:8511`), значит для фиксированного выхода и
фиксированной метки хеш не меняется, пока не придёт новый блок.

Свежие пробы приходят двумя путями: по одному слоту на выход каждые `POS_SCAN_STEP = 15`
секунд, когда часы двигают верх окна, и залпом — при появлении любого нового блока,
когда обнуляется весь перебор.

**Следствие:** PoS-блоки идут очередями. Выиграл — модификатор сменился — новая попытка
на следующем холостом тике кошелька (`wallet_rpc_idle_work_period_ms = 2000`);
промахнулся — ждать PoW-блока. Замер на стенде: 54 интервала вплотную против 31
нормального. **Распределение интервалов PoS не пуассоновское по устройству протокола**,
и требовать от него «медиана ≈ 0,693 × среднего» неверно. Критерий для PoS-стороны —
доля блоков и длина очередей.

### Окно перебора отсчитывается от медианы, а темп связывает обе стороны

`scan_pos` (`wallet2.h:1193`) берёт низ окна из `starter_timestamp`, который демон
отдаёт как медиану последних `BLOCKCHAIN_TIMESTAMP_CHECK_WINDOW = 60` блоков
(`core_rpc_server.cpp:1309`), а верх — как `get_core_time() + CURRENCY_POS_BLOCK_FUTURE_TIME_LIMIT - 5`,
то есть `now + 1195`. Перебор идёт симметрично от середины окна.

Пока блоки быстрее цели, шестьдесят блоков не покрывают 1195 секунд, вся история
оказывается в будущем, медиана прижимается к вершине и середина окна ползёт к потолку.
Замерено: медианный дрейф метки PoS +843 с, максимум +1195 при потолке 1200.

Дальше это бьёт по PoW: драйвер ставит честное время, а демон отвергает блок с
`Timestamp ... less than median of last 60 blocks` — 29 отказов из 59 попыток. Часть
времени демон не может даже собрать шаблон: `Block template construction failed because
current core timestamp ... is less than median`.

**Следствие:** перекос такта и голод PoW — не две болезни, а одна. После починки
стартовой сложности дрейф ушёл в −324…+451, отказы PoW обнулились.

⚠️ Отдельно: `get_adjusted_time()` (`blockchain_storage.cpp:6583`) возвращает
`m_core_runtime_config.get_core_time()`, а не медиану — там стоит
`//TODO: add collecting median time`. Проверка потолка будущего честная, по часам;
петли обратной связи внутри неё нет.

### Ограничитель серий выключен порогом высоты

`blockchain_storage.cpp:7970` отвергает PoS-блок при `sequence_factor >
BLOCK_POS_STRICT_SEQUENCE_LIMIT = 20`, но только выше
`BLOCKCHAIN_HEIGHT_FOR_POS_STRICT_SEQUENCE_LIMITATION` — 57000 в мейннете, 18000 в
тестнете. На стенде высотой в сотни блоков механизм молчит, и серии доходили до 126
подряд. Зеркальный гейт есть на стороне кошелька: демон отдаёт
`pos_sequence_factor_is_good` (`core_rpc_server.cpp:1302`), кошелёк его слушает
(`wallet2.cpp:5462`) и перестаёт майнить. Опускание порога до нуля под `ZANO_SIMNET`
включает оба и срезало максимум со 126 до 13.

`correct_difficulty_with_sequence_factor` (`currency_format_utils.cpp:643`) — не
ограничитель: он умножает вклад блока в кумулятивную сложность на `0,75ⁿ`, то есть при
длинной серии стирает его в ноль, а не запрещает её.
